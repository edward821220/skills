# Rule 1 - 系統介面盤點必須從需求部位出發

- Level: `MUST`
- 盤點系統介面時，必須先從需求原文中可辨識的使用者行為、外部依賴、資料責任或運作邊界切出需求部位，再回推對應的技術端點類型。
- 不可先預設「一定會有前端、後端、資料庫」之類的固定技術清單，再反向替它們補需求理由。
- 若某個介面無法指出它是從需求哪一段推得，表示尚未被充分論證，不應寫入盤點結果。

## Good Example

- 這個例子是好的，因為介面從需求的付款、開通與查詢責任推導，而非先列技術清單。

````md
1. `前端訂閱與結帳介面`
   - 端點類型：`前端端點`
   - 主要介面：方案列表頁、結帳表單、付款結果頁
   - 需求原文依據：需求要求「使用者可以瀏覽訂閱方案」、「使用信用卡付款」。
````

## Bad Example

- 這個例子是壞的，因為先列技術端點再硬湊理由，沒有真的從需求部位盤起來。

````md
1. `前端` — 通常系統都會有前端。
2. `後端` — 通常系統都會有 API。
3. `資料庫` — 感覺之後應該會需要。
````

# Rule 2 - 每個介面必須交代端點類型、主要介面與需求原文依據

- Level: `MUST`
- 每個盤點出的介面至少包含三個欄位：`端點類型`（前端、後端、資料庫、第三方、手機端、硬體端、雲端或其他）、`主要介面`（後續分析聚焦的入口、契約、資料責任或操作面）、`需求原文依據`（引用需求中的具體句子、需求摘要，或已成形的 `FR` / `NFR` / 關鍵實體，不得只寫抽象判斷）。

## Good Example

- 這個例子是好的，因為三個欄位完整，可直接接到後續拆票。

````md
1. `訂單與訂閱持久化介面`
   - 端點類型：`資料庫端點`
   - 主要介面：使用者、訂單、付款紀錄、訂閱狀態與重試資料欄位
   - 需求原文依據：需求要求「後台查得到訂單與付款狀態」以及「付款成功後立即開通會員權限」。
````

## Bad Example

- 這個例子是壞的，因為只有名稱，沒有揭露後續拆票所需的核心欄位。

````md
1. `資料庫`
````

# Rule 3 - 只有在責任邊界獨立時才拆成獨立介面

- Level: `SHOULD`
- 多個需求部位落在同一類技術端點，但分析責任、相依關係或後續票的歸屬明顯不同時，才拆成不同介面。
- 會由同一組分析視角、同一份契約或同一張票處理的需求部位，應優先合併，避免盤點過碎。
- 不應因為某端點底下有多條 API、數個頁面或數張資料表，就自動全部拆成獨立介面。

## Good Example

- 這個例子是好的，因為只在責任邊界真的不同時才分開盤點。

````md
1. `後端訂單與訂閱 API 介面` — 建立訂單、接收付款結果、開通訂閱
2. `訂單與訂閱持久化介面` — 訂單、付款與訂閱狀態持久化
````

## Bad Example

- 這個例子是壞的，因為把同一個後端責任切得過碎，卻沒有提供新的拆票價值。

````md
1. `建立訂單 API`
2. `查詢訂單 API`
3. `Webhook API`
4. `付款狀態 API`
````

# Rule 4 - 每個介面必須標記對既有系統的影響

- Level: `MUST`
- 每個介面標記 `ADD` / `MODIFY` / `DELETE` / `NOOP` 其中一種影響：
  - `ADD`：新增端點、契約、表、頁面或行為，既有系統不需修改。
  - `MODIFY`：改變既有 contract、schema、端點行為或資料語意；必須指出受影響的既有對象。
  - `DELETE`：移除既有行為、端點或資料；必須指出被移除對象與依賴它的行為。
  - `NOOP`：介面存在但本輪不改，僅供相依分析參考。
- `MODIFY` 與 `DELETE` 未指出受影響對象時，視為盤點未完成。

## Good Example

- 這個例子是好的，因為影響標記點出受影響的既有對象，相依關係一目瞭然。

````md
1. `後端訂單 API 介面` — `MODIFY`：`POST /orders` 回應新增 `retry_token` 欄位
2. `訂單持久化介面` — `MODIFY`：`orders` 表新增 `retry_count` 欄位
3. `訂閱開通知介面` — `ADD`：新 webhook consumer
````

## Bad Example

- 這個例子是壞的，因為標了 MODIFY 卻沒說改到什麼既有對象，相依分析無法進行。

````md
1. `後端 API` — `MODIFY`
````

# Rule 5 - 依真實共用成果與部署限制辨識 sequential dependency

- Level: `MUST`
- 判斷相依要看是否需要同一份先行成果，不只看是否 `MODIFY` 同一個 contract、schema、migration、shared state 或檔案；共用修改位置本身不構成 blocking edge。
- 多張候選 slice 依賴同一份必須先完成的共用成果，或部署、相容性限制要求分階段落地時，將必要成果列為獨立前置票候選，不讓平行票重複實作同一份成果。
- migration 若只服務單一 slice，且可與其一起安全落地及驗證，優先合併在同一票；合併不免除票內正確的 migration 與部署順序。
- 前置技術票是 vertical slice 的必要例外，必須有明確交付成果、可驗證性與真實下游相依；不因前端、後端或資料庫分層就自動拆票。
- 每個 dependency 候選都要記錄「誰依賴誰、所需先行成果或部署限制是什麼」，供拆票階段確認 blocking edge。

## Good Example

- 這個例子是好的，因為共用先行成果才獨立切票，單一 slice 的 migration 不會被強制拆開。

````md
- 前置票：`orders` 表加 `retry_count`、`retry_token` migration
- 相依票 A：重試 API（依賴前置 migration）
- 相依票 B：後台重試狀態顯示（依賴前置 migration，可與 A 平行）
- 另一個單一 slice：新增只由本 slice 使用的 retry_note 欄位、API 行為與測試 -> 同一票安全落地，不另拆 migration 票
````

## Bad Example

- 這個例子是壞的，因為重複實作共用成果，或只因修改同一個對象就捏造相依。

````md
- 票 A、B 都依賴相同 retry_token 語意，卻各自建立欄位與定義 -> 共用成果無唯一歸屬。
- 票 C、D 修改 orders 表中互不依賴的行為，只因碰到同一張表就宣告 C blocked by D -> 不是真實相依。
````
