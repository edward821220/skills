# Rule 1 - 每次寫入 Notion 前依 speak-human-tw 的確認模式把關

- Level: `MUST`
- 所有送進 Notion 的作者撰寫文字都必須先過把關：釐清留言、票標題與內文、blocker fallback、補充說明與任何其他寫入欄位。
- 執行方式：完整讀取 `../speak-human-tw/SKILL.md`（相對於本 skill 目錄），依其現有流程檢查文字、鎖定保護清單並保真回讀，只把完成把關的文字送進 Notion。
- 互動執行時，若尚未選定本工作流的模式，先請主管選擇「保留確認清單」或「跳過確認、事後摘要」；在主管對話中保留選擇，未選定前不得自行跳過確認。非互動執行依下游既有規則處理。
- 選擇保留確認清單時，依下游要求列出全部建議修改並等待選項，只套用核准項目；選擇跳過確認時，將修改總數與原句／原因／改成了什麼回報主管，不混入 PM 問題留言。
- 每次寫入都重新執行文字檢查；同一工作流的確認模式不必重問，文字性質明顯改變時依下游要求重新確認。
- 跳過文字確認不代表跳過 PM 產品決策 gate 或主管拆票核准，不得藉潤飾改變已核准的產品行為、票邊界或相依。

## Good Example

- 這個例子是好的，因為確認模式已獲授權，文字把關與產品核准仍各自成立。

```text
發布 OQ comment 前：
1. 完整讀取 ../speak-human-tw/SKILL.md；主管已選擇「跳過確認、事後摘要」
2. 鎖定保護清單、依下游流程檢查文字並保真回讀
3. 發布把關後的問題；修改摘要回報主管，不放進 PM 留言
```

## Bad Example

- 這個例子是壞的，因為沒有取得跳過文字確認的授權，也沒有完成把關。

```text
發布 OQ comment 前：
1. 寫好問題草稿，因為主管核准了拆票，就自行視為也核准跳過文字確認
2. 不檢查保護清單，直接送出
```

# Rule 2 - 把關只潤飾文句，保留清單內容原樣不動

- Level: `MUST`
- 下列內容必須原樣保留，不參與語氣潤飾：模板結構與 section 標籤、`OQ-###` 與草稿識別碼、`blocking` / `assumed` 標記、程式識別字、API path、schema 名稱、enum 值、產品名稱、連結、Notion property 精確值。
- speak-human-tw 的風格規則作用於保留清單以外的周圍文句；潤飾不得改變事實、決策、需求或驗收內容。
- 潤飾後若發現文句與來源事實有出入，以來源為準修回，不保留較好讀但不準的版本。

## Good Example

- 這個例子是好的，因為只動了說明文字，`OQ-###`、enum 與事實內容原樣。

```md
潤飾前：OQ-011 asks whether RETRY_PENDING status orders are in scope
潤飾後：OQ-011 詢問 `RETRY_PENDING` 狀態的訂單是否納入範圍
```

## Bad Example

- 這個例子是壞的，因為為了語感把 enum 值翻譯、也把 blocking 改成 assumed，改變了事實。

```md
潤飾後：OQ-011 詢問「重試中」狀態的訂單是否納入範圍（順便改成 assumed 比較順）
```
